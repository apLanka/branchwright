# Maintaining a verification skill

A feature map rots when the app changes. This is the upkeep loop for a skill generated by `create-verification-skill` (any project-local skill with launch and drive sections and a feature map). The unit of rigor is the feature: cover every feature file from source and exercise every feature live.

## Outcomes (say which)

- **clean:** every feature got source and live coverage; nothing to ship. No branch.
- **changed:** one task branch ships proven corrections to the doc, harness or map, taken through the normal workflow (`ready`, user confirms, `finish-task`).
- **blocked:** coverage could not finish or a proven fix could not ship safely. Say exactly what blocked it.

## Edit scope

Only the verification skill's own directory (`SKILL.md`, `features/`, scripts it owns). Never product code during this run: a behavior the map describes that the app no longer has is either doc drift (fix the map) or a product regression (report it, do not paper over it in docs).

## Pass

0. **Locate the target:** the project-local skill with launch/drive sections and a feature map (usually `.opencode/skills/verify-*/`). Several candidates: pick by the user's words or ask; none: point at `create-verification-skill` rather than inventing a target.
1. **Index hygiene.** Read `features/README.md` and glob its siblings; fix missing, extra, duplicate or dead entries.
2. **Source wave.** One read-only subagent per feature file, in parallel. Each explains how the feature works from source, flags likely doc drift with citations, and returns one live-verification recipe. Children never drive the app and never edit files. Return shape: summary, source entry points, likely drift or none, one recipe.
3. **Reconcile.** Every feature file has a summary. Merge overlapping recipes into few app states; spot-check cited drift; sweep recent churn (`git log` on source dirs) for user-facing surfaces missing from the map, requiring a concrete source path before calling one missing.
4. **Live pass**, required even when source looks clean. You own all driving, following the skill's own Launch section (one long-lived instance driven serially for servers and UIs; a fresh isolated session per drive for short-lived CLIs). Exercise every feature at least once; keep the evidence outside what teardown removes.
5. **Triage.** Wrong or missing description: fix the map. Working behavior the harness cannot drive: fix the harness (scripts executable, invocation shown in the skill body). Actually broken app behavior: a product gap; report it to the user, keep it out of this branch.
6. **Ship or stop.** For changed: re-read every changed file, then the normal workflow. For clean or blocked: report the outcome and coverage honestly.

Keep run notes (features covered, unreachable prerequisites, confirmed drift, outcome) in `.workflow/`; do not commit them.
